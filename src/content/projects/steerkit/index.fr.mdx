## Contexte

Steerkit est né du vol des fées dans [Ocarina](/fr/work/ocarina/) : quelques centaines de lignes de calcul vectoriel qui les faisaient voler vers une cible, ralentir, planer et s'écarter de la caméra. Je voulais le même mouvement dans d'autres projets et je n'ai **rien trouvé d'assez petit pour l'emporter**. [Yuka](https://github.com/Mugen87/yuka), la bibliothèque la plus proche, est un framework complet d'IA de jeu construit autour de ses propres vecteur, véhicule et gestionnaire d'entités. J'ai donc extrait le module dans une bibliothèque à part, avec l'[article de Craig Reynolds à la GDC 1999](https://www.red3d.com/cwr/steer/gdc99/) comme spécification, et je m'en suis servi pour publier un paquet comme j'aimerais en dépendre.

## Contraintes

- Un behavior tourne pour chaque agent, à chaque frame. Avec mille agents à 60 fps, tout objet créé par appel est **un déchet que le ramasse-miettes doit balayer**, et ses pauses se voient en saccades.
- Il fallait travailler sur les vecteurs qu'un projet a déjà : `THREE.Vector3`, des objets simples, les types d'un autre moteur. Aucune dépendance à l'exécution.
- Le steering se règle à l'œil. Sans voir les forces, **chaque paramètre est une supposition**.
- Un projet qui n'a besoin que de `seek` ne doit pas payer pour le flocking.

## Approche

Tout `{ x, y, z }` est un vecteur. Le typage structurel de TypeScript laisse **passer `THREE.Vector3` tel quel**, donc un agent peut prêter la `position` de son propre mesh, et `step` déplace directement le mesh. Une classe de vecteur à moi aurait imposé de copier à l'entrée et à la sortie à chaque frame.

Chaque behavior prend l'agent en premier et écrit sa force dans **un vecteur `out` passé en dernier**, qu'il renvoie. Renvoyer un nouveau vecteur se lit un peu mieux et alloue à chaque appel. Toutes les entrées sont lues avant d'écrire dans `out`, donc `out` peut être n'importe laquelle d'entre elles, et un test le vérifie.

```ts
import { arrive, blend, keepAway, step } from "steerkit";

const fairy = {
  position: mesh.position, // un THREE.Vector3, tel quel
  velocity: new THREE.Vector3(),
  maxSpeed: 2,
  maxForce: 4,
};
const [force, goal, away] = [vec(), vec(), vec()]; // créés une fois

// À chaque frame
blend(
  force,
  [arrive(fairy, target, { slowingDistance: 1.2 }, goal), 1],
  [keepAway(fairy, camera, { radius: 1 }, away), 2],
);
step(fairy, force, dt);
```

C'est en combinant les forces que bien se lire et ne rien allouer se séparent. `blend` et `prioritize` prennent leurs forces en arguments et créent de petits tableaux à chaque appel ; `zero`, `add` et `addWithin` écrivent les mêmes sommes sans eux. J'ai **gardé les deux formes** et documenté quand passer de l'une à l'autre : trois agents prennent la plus lisible, une foule l'autre. Three.js vit dans une entrée optionnelle `steerkit/three`, avec `three` en peer optionnelle : le cœur ne l'importe jamais.

Chaque behavior a sa page de démo, prérendue pour la recherche et les aperçus de liens, avec les forces dessinées et un curseur pour chaque paramètre. Un bouton Copy prompt donne à un agent de code l'objectif, les valeurs choisies sur la page et un lien vers `llms.txt`, dont la section API est générée à partir des sources de la bibliothèque avec le compilateur TypeScript. Les exemples du README tournent comme des tests, donc aucun des deux ne peut s'écarter du code.

## Notes d'ingénierie

Zéro allocation n'est **qu'une promesse tant qu'on ne l'a pas mesuré**. Le test d'allocation lit `total_allocated_bytes` de V8 autour de 50 000 appels de chaque behavior et échoue quand un appel alloue un objet. Il a trouvé ce que la lecture du code n'avait pas vu : `Math.hypot` alloue un tableau temporaire quand V8 n'optimise pas l'appel, donc les normes utilisent `Math.sqrt`, et `Math.random` alloue aussi, donc les tests utilisent un générateur avec graine sur un tableau typé.

Le cas subtil était le **boxing**. V8 range un nombre sur le tas quand il traverse un appel qu'il n'a pas inliné, et dans une grosse frame son budget d'inlining s'épuise. `keepAway` appelait `flee`, n'allouait rien seul et fuyait au milieu d'une foule. Il calcule désormais sa force dans des variables locales, et les boucles sur les voisins n'appellent plus aucune fonction utilitaire. Pour 1 000 agents qui combinent `wander`, `arrive` et `keepAway`, les déchets sont passés d'environ 5 Kio à environ 1 Kio par frame.

Un test ne repère ça que si le code tourne comme dans une frame, donc un benchmark Node simple sert de seconde vérification, chaque variante dans son propre processus pour que le JIT n'optimise pas les fonctions partagées pour celle qui a tourné en premier. Sur un M1 Pro avec Node 26, le `blend` lisible laisse environ 190 Kio de déchets par frame pour 1 000 agents, contre environ 1 Kio avec `zero` et `add`. Pour 1 000 boids, une grille spatiale triée une fois par frame, d'après les [Ten Minute Physics](https://matthias-research.github.io/pages/tenMinutePhysics/) de Matthias Müller, fait passer une frame **de 12 ms à 0,7 ms**.

Des tests de propriétés avec fast-check lancent des valeurs aléatoires et extrêmes sur chaque fonction et vérifient que les sorties restent finies, les vitesses sous `maxSpeed` et les forces sous `maxForce`.

## Résultat

Steerkit est sur npm en 0.4, sous licence MIT : 18 behaviors, les combinateurs, une grille spatiale et l'adaptateur Three.js, 4,1 kB minifiés et compressés en brotli en tout, et 170 o pour `seek` seul. **Les fées d'Ocarina volent désormais avec lui** : `arrive`, `brake`, `keepAway` et `step` ont remplacé les forces écrites à la main, et `faceVelocity` la rotation faite maison. Les versions passent par Changesets et sont mises en attente sur npm avec provenance, puis approuvées avec une double authentification avant que quiconque puisse les installer.
